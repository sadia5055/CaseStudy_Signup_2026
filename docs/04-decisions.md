# 04 — Decisions

Format: context → choice → trade-off. Newest at the bottom.

**D1 — Playwright + TypeScript.** The brief allows Cypress or Playwright and prefers TypeScript. Playwright was chosen for built-in projects (used for languages), network interception on the same page as the UI, and parallel workers. TypeScript was chosen because:
- **nesto prefers it**, and the front end is a Next.js app, so the tests are in a language the team already reads.
- **The compiler enforces things this suite relies on:** `en.ts` and `fr.ts` must both implement the `Copy` type, so a missing translation fails the build; user data and the form → request → response expectations are typed; the response contract (zod) infers its types.
- **Type-aware lint catches missing awaits** (`no-floating-promises`), the most common silent bug in async browser tests.
- **Playwright's own API and docs are TypeScript-first**, and Playwright runs `.ts` directly, so there is no separate build step.

Trade-off: a little more setup (`tsconfig`, typed ESLint) than plain JavaScript, and a dependency pin (D13). The suite is kept small enough to defend line by line.

**D2 — Language as Playwright projects.** Alternatives: duplicate spec files (drift), a `LANG` env var read inside tests (hidden branching), a loop over languages inside each spec (unreadable reports). Projects give one command per language, separate report entries and no branching in specs. Trade-off: everything runs twice, so account-creating tests are kept few.

**D3 — Verify the UI-triggered request, not a direct API call.** The requirement is that the account-creation call made by the form returns 201 and contains what was entered. A direct `request.post` would not prove the form sends the right payload. The response listener is registered before the click. Trade-off: the test depends on the UI to reach the API; direct API tests are listed as future work.

**D4 — Three separate integration assertions (form → request → response → contract).** One big `toEqual` would say "something differs". Separate hops say where. Trade-off: slightly longer specs.

**D5 — zod subset contract with `passthrough`.** The account object has 60+ fields, most irrelevant (`*Specified` flags, tracking). Asserting all of them would break on harmless additions. Trade-off: a new field is not detected; the "no secrets echoed" rule is checked separately by key name.

**D6 — Email domain `mailinator.com`, configurable via `EMAIL_DOMAIN`.** Discovery showed `example.com` is rejected by the server (`placeholder email detected`), and the brief asks for throwaway addresses. Public inboxes are readable by anyone, so only fake data is used. Trade-off: if nesto blocks the domain, set `EMAIL_DOMAIN`; open question for nesto.

**D7 — Mock only failures.** `page.route` is used for 500/422/abort cases that cannot be triggered on demand. The success response is never mocked, because the brief asks for validation of the real integration.

**D8 — One page object, no base classes.** One page under test. A hierarchy would be structure without content.

**D9 — Five device profiles × two languages in the default run.** The page is customer-facing with heavy mobile traffic, so desktop Chrome, Firefox, WebKit, a Pixel 7 (Chromium, touch) and an iPhone 14 (WebKit, touch) all run by default. Alternative considered: Chromium only plus a "later" list; rejected because the first phone run immediately found a test gap (the language switch is behind a hamburger menu) and a mobile-only layout bug would otherwise ship unseen. Trade-off: a full run is 290 tests and creates 30 accounts in QA; `npm run test:chrome` gives a 6-account quick run. These are emulations, not real devices (README limitation).

**D10 — Default `data-testid`, used sparingly.** The app already exposes `data-testid`, which is Playwright's default, so no config is needed. Accessible locators come first; test ids are for controls whose accessible name is weak.

**D11 — Wait for the geolocation response, then fill and verify.** The form re-initialises after the page loads: values typed too early are wiped, which shows up as unrelated "required" errors and looks like a validation bug. A first fix (wait for React hydration, verify each value after filling) still failed 8 of 40 runs, with a different set of tests each time, so the reset happens after the point where a value can be verified. Every load calls `GET /api/geolocation/all`; waiting for that response before interacting made the UI suite pass 120 of 120 runs (20 tests × 2 languages × 3 repeats). The cause is inferred from that result, not proven from the app's source. (Superseded in part by D19, and the readiness signal was strengthened by D21.) The page object also keeps a fill-and-verify loop (`toPass`) for the phone field, which reformats input. No fixed sleeps.

**D12 — Retries.** 0 locally, 1 in CI, so a transient network error shows up as "flaky" in the report instead of failing the build silently. Intermittent failures are investigated (D11 came from one), not hidden behind retries.

**D13 — TypeScript 6.0, not the latest 7.x.** `typescript-eslint` supports `<6.1`; TypeScript 7 made `npm install` fail with a peer-dependency conflict. Type-aware lint rules (`no-floating-promises` catches a missing `await` on a Playwright call) are worth more here than the newest compiler. Revisit when `typescript-eslint` supports 7.

**D14 — No traces or video; an allowlisted exchange is attached instead (revised by D22).** A Playwright trace embeds every request and response body, and the signup response contains an access token. Each account-creating test attaches an exchange summary. It was first a copy with password and token fields replaced by `[REDACTED]`; that denylist still carried the email, names, phone and ids, so D22 replaced it with an allowlist. Trade-off: no trace viewer for CI failures; run locally with `--trace on` when debugging (throwaway QA data).

**D15 — CI is manual/PR/push only, no schedule.** Every run creates accounts in a shared QA environment, and nesto has not confirmed that runs from GitHub-hosted machines are welcome (assumption A7). A nightly job should wait for that answer.

**D16 — Credential exposure in test reports (superseded by D22).** This entry originally said the leak happened only when a test fails, through `error-context.md`, and accepted it. That was incomplete and the decision was wrong. Playwright also writes the typed value into step titles of the HTML report on **passing** runs, CI uploaded that report on every run, and the repository is public, so valid generated credentials for throwaway QA accounts were published routinely. Throwaway data does not make routine publication of working credentials acceptable. Audit, scope and remediation: [`07-security-remediation.md`](07-security-remediation.md).

**D17 — The language switch branches on visibility, not on device.** On wide screens the switch is a header link ("FR"/"EN"); on phones it is a "Language" picker inside the hamburger menu (a React Aria menu button whose items have role `menuitemradio`). `switchLanguage()` waits until either control is visible and uses whichever is. Alternatives: an `isMobile` check in the spec (breaks for tablets and resized windows, and puts branching in tests) or separate mobile specs (duplication). Found because F-04 failed on all four phone projects.

**D18 — Layout checks are measurements, not screenshots.** L-01…L-03 assert numbers (page overflow, control boxes, longest error message) that fail with a value, and run on every project. Visual-diff screenshots were rejected: they need baselines per browser, language and device (20 images), and any font rendering difference makes them noisy. Trade-off: the checks catch overflow and clipping, not visual polish. The overflow measurement was validated by injecting a 2000px element (0 → 1610 px).

**D19 — Pin the visitor's location with a stub.** The first CI run failed on all ten projects: F-02 expected Ontario, and CI got an empty province. The page pre-selects the province from `GET /api/geolocation/all`, which looks up the visitor's IP through third-party services, so the result depends on where the suite runs; one CI run also saw that endpoint not answer within 45 s, which my readiness wait (D11) turned into a 45 s timeout on unrelated tests. The fixture now stubs the response with a fixed Ontario location. Two tests pin the behaviour explicitly: F-02 (Ontario → province preselected) and F-05 (Virginia, US → province empty, which is what CI saw). Alternatives: assert "any value" for the province (hides the behaviour), or keep the real lookup and accept flakiness (CI-dependent, and an outage of a third-party service would fail the signup suite). Trade-off: the geolocation behaviour is simulated, not live; it is not the signup path, and the account-creation call is still never stubbed.

**D20 — 30 s for the post-signup redirect, 60 s per test.** After the 201 the app signs the user in through Auth0 on `auth.qa.nesto.ca` and then lands on the quote page. On CI runners that round trip took over 10 s (P-01 failed on chrome and WebKit, flaked on Firefox). The redirect check stays, because landing on the quote page is the visible outcome of a signup, but it now waits up to 30 s and the per-test timeout is 60 s. Confirmed once: the next CI run passed all six jobs. One green run is not a stability record; if it flakes, the check should be reduced to "left the signup page".

**D21 — Ready means the inputs have distinct ids.** After D19 one test failed once in the full run (`fr-webkit` L-02: `getByLabel` matched 6 inputs). Repeating it reproduced the failure 3 times in 30. A probe that only loads the page showed why: with the stubbed geolocation, 15 of 40 WebKit loads had every input sharing `id="field-1"` at the moment the page object declared the page ready, and 0 of 40 one and a half seconds later; with the real (slower) response, 0 of 40; Chromium and Firefox 0 of 40 either way. The instant stub made the response arrive before React finished hydrating, and "response received + React root exists" was too weak a signal. The page object now also waits until every form input has a unique id (a state, not a delay). Result: 80 of 80 on `fr-webkit` and `en-webkit`. This was a flaw in my test infrastructure, not an app defect: a real visitor's geolocation answer is never instant. The probe is `scripts/duplicate-id-probe.mjs`.

**D22 — Keep secrets out of Playwright's output at the source.** Measured with canary values (Playwright 1.65.1): `fill`, `type` and keyboard calls render their argument into step titles; a boxed step does not hide them; a failure copies typed values into `error-context.md`; `toHaveValue` and `toMatchObject` print values; raw attachments carry the email and ids. The generated email and passwords are therefore entered through `evaluate` (title: "Evaluate", under a step named after the field), retry checks and assertions compare booleans or field names, the attached exchange is an allowlisted projection, and `PLAYWRIGHT_NO_COPY_PROMPT=1` stops the page snapshot. The redirect check after signup prints the path only (`expectToLandOn`), because `toHaveURL` prints the full URL and the app's OAuth login URLs carry `code`, `state` and client ids. Rejected: redacting generated files afterwards (the report embeds zipped data, formats change between versions, and a missed pattern publishes the value), and relying on boxed steps (measured: they do not work). Trade-offs: the secret fields are not typed key by key (no per-keystroke events, no trusted `input` events), though a real click and Tab and the `beforeinput`/`input`/`change` events are produced; on the real form, validation errors and request payloads matched real typing in 11 cases on three engines, and the app has no blur or change validation (see `07-security-remediation.md`). The environment variable is not a documented option and the documented reporter option `noCopyPrompt` was measured not to prevent the leak, so D23 pins the variable's effect and it is one of five layers.

**D23 — A canary regression test guards the fix.** `npm run test:security` runs the real fixtures, page object and helpers with synthetic canaries against a local fake server (no QA accounts), with passing and deliberately failing scenarios, then scans every output, including nested zips and encoded forms. A scanner self-test, a leaky control that must be detected, and mutation checks keep a green result meaningful. Alternatives: a grep step in CI only (it cannot know what to look for in a real run, and finds nothing if the pattern is wrong) and scanning a real QA run (creates accounts to prove a negative). Trade-off: a fake server mimics the real page only as far as the page object needs.

**D24 — CI publishes an allowlisted summary, never raw reports.** The JSON report stays on the runner; `scripts/summarize-results.mjs` reads only titles, project, outcome, duration, attempts and totals, so a dirty report still yields a clean summary (tested). `security/upload-gate.mjs` fails the job on credential-shaped content. The workflow runs with `contents: read`, checks out without persisted credentials, skips the QA tests for pull requests from forks, and starts them only after the security job passes. Trade-off: no raw report or screenshot is available from CI; debugging a CI failure means reproducing it locally.

**D25 — Two workers, locally and in CI.** Measured on an 8-logical-CPU laptop: at 4 workers CPU averaged 93% and Firefox tests ran about 3× slower than with 1 worker, which produced `en-firefox` timeouts when the machine was also busy; 2 workers had the best Firefox wall time. A/B runs of the old and current code were indistinguishable, and QA latency was stable, so the cause is contention, not a synchronization problem or QA. The 60 s timeout stays: raising it would hide contention. Trade-off: fewer parallel tests on a bigger machine (override with `--workers`). Evidence and remaining uncertainty: [`08-firefox-reliability.md`](08-firefox-reliability.md).
